#+begin_abstract
Learned representations shape how models organize information and generalize
beyond their training examples. As learning systems evolve to incorporate
information from increasingly diverse modalities, a flexible and efficient
foundation for representation-learning research becomes essential to enable
progress. We introduce Representax, an open-source JAX framework for developing
and training representation-learning models across modalities. Representax
unifies extensible training and evaluation tasks with established methods
spanning dense and late-interaction retrieval, multimodal contrastive learning,
reward modeling, and joint-embedding predictive learning. Its shared training
infrastructure supports model adaptation, multimodal data processing,
memory-efficient optimization, and distributed execution on GPUs and TPUs. To
demonstrate its capabilities, we compare training performance against established
frameworks, train and evaluate retrieval and multimodal models, and measure
multi-GPU strong scaling. These experiments demonstrate competitive throughput,
improvements on held-out retrieval tasks, and efficient scaling. Representax
provides a foundation for investigating how representations are learned and
adapted, and for taking new ideas from exploration to scale.
#+end_abstract

* Introduction
:PROPERTIES:
:CUSTOM_ID: sec:introduction
:END:
Representation-learning research requires more than an encoder and a loss.
An experiment must turn raw observations into model inputs, specify which
relationships a representation should preserve, and evaluate whether the
learned structure transfers beyond the training examples. Adding another
modality also adds practical decisions about decoding, sampling, sequence
shapes, and memory. These decisions are part of making a method usable, but
rebuilding their infrastructure for each objective makes research harder to
extend and compare.

We develop Representax around a simple aim: let researchers change what a
model learns without reconstructing how a training job runs. Native Equinox
models, task-specific objectives, and configurable data pipelines share
optimization, evaluation, checkpointing, and distributed execution. The
library includes established methods for retrieval, multimodal contrastive
learning, reward modeling, and joint-embedding prediction, providing starting
points as well as interfaces for new methods. Its contribution is this shared
research infrastructure, not a new compiler or representation-learning
objective.

The design separates scientific choices from execution choices. For example,
the contrastive negative pool is part of an objective, whereas encoder chunk
size determines how that objective is evaluated under a memory constraint.
Keeping these decisions explicit helps researchers tune execution without
silently substituting a different experiment. The separation is an interface
discipline, not a guarantee that arbitrary configurations are equivalent;
supported combinations require numerical and workload-specific checks.

We evaluate three questions: (1) how training throughput compares with maintained
reference implementations, (2) whether the framework supports useful held-out
learning in complete adaptation runs, and (3) how a fixed training workload
scales across GPUs. Results are favorable in many measured settings but not
uniformly: backend choice, input processing, compilation and interconnect
constraints materially affect the outcome.

Paired runs measure performance, longer adaptation runs test useful learning,
and fixed-work scaling tests distributed execution. None alone establishes
all three. We release the implementation and experiment configurations as a
basis for further research, not a closed collection of benchmarks.

* Related Work
Research libraries contribute through their interfaces, implementations, and
the experiments they make practical. Equinox expresses parameterized functions
as callable PyTrees and filters JAX transformations [cite:@kidger2021equinox].
Scenic emphasizes rapid experimentation and GPU/TPU execution
[cite:@dehghani2022scenic], while solo-learn combines extensible visual
representation-learning methods with efficient pipelines
[cite:@dacosta2022sololearn]. JaxPruner demonstrates the value of a common
interface and ecosystem integration [cite:@lee2023jaxpruner].
Stable-Baselines3 emphasizes reliable implementations and reference comparisons
[cite:@raffin2021stablebaselines]. Representax follows this research-toolkit
direction, organizing representation learning across objectives and modalities
around a shared training lifecycle.

Task-focused frameworks provide important reference points. Sentence
Transformers builds on bi-encoder sentence representations
[cite:@reimers2019sentencebert]; PyLate supports ColBERT-style token-level
retrieval [cite:@khattab2020colbert;@chaffin2025pylate]. CLIP establishes a
widely used image-text contrastive formulation [cite:@radford2021clip], while
V-JEPA 2.1 learns dense video features through joint-embedding prediction
[cite:@murlabadia2026vjepa]. Representax does not replace these scientific
contributions. It implements their task families in a common JAX system and
evaluates concrete integrations against PyTorch-based references
[cite:@paszke2019pytorch].

Gradient caching [cite:@gao2021gradcache], Matryoshka objectives
[cite:@kusupati2022matryoshka] and low-rank adaptation [cite:@hu2021lora]
are established techniques, not new algorithms introduced here.
Jina's geometry-preserving multimodal adaptation motivates the connector-only
arm of our text-anchored study [cite:@honicke2026jina]. Our experiments test
whether this breadth can share an extensible training system with practical
performance; they do not compare every library's complete feature set.

** Models, Tasks, and Evaluation
An encoder accepts model-native inputs and an explicit semantic route, such
as query or document. Its processor owns tokenization and modality-specific
payload preparation. Models remain Equinox PyTrees rather than opaque objects
owned by a separate trainer. A task interprets a batch and returns a scalar
loss and named metrics through ~loss(model, batch, key=...)~.

Some objectives expose an additional representation boundary:
=representations= performs encoder computation, and
=loss_from_representations= evaluates the objective from those outputs.
This lets modifiers reuse an encoder pass. Matryoshka training, for example,
applies weighted losses to normalized embedding prefixes. A basic scalar-loss
task need not expose this interface; specialized execution paths validate
their required capabilities. Joint-embedding predictive tasks additionally
support a post-update transition for a target encoder updated without
gradient descent.

Evaluation separates traced per-batch computation from host-side accumulation
and finalization. Corpus-level retrieval metrics need not be approximated by
averages of minibatch metrics or embedded in the optimizer step. Complete
runs use a =JobConfig= to construct the model, task, data, optimizer and
training settings. Adapter insertion and trainable-parameter selection are
orthogonal: adding LoRA does not require freezing every other module.
The multimodal study uses this distinction to train connectors alone,
connectors with adapters, or all parameters. Appendix [[#sec:example]] gives
a small executable composition example.

** Memory-Efficient Objectives
Contrastive objectives couple examples through a negative pool. Ordinary
accumulation over independent microbatch losses changes that pool.
For paired embeddings \(z_i=f_\theta(x_i)\), \(u_i=g_\theta(y_i)\), a
standard asymmetric objective is
\[
\mathcal L=-\frac{1}{B}\sum_{i=1}^{B}
\log\frac{\exp(s(z_i,u_i)/\tau)}{\sum_{j=1}^{B}\exp(s(z_i,u_j)/\tau)}.
\]
Here \(s\) is similarity and \(\tau\) is temperature. The symmetric form
averages the two retrieval directions. GradCache separates differentiation
of this full-batch objective from encoder replay [cite:@gao2021gradcache]:
\[
\nabla_\theta\mathcal L=
\sum_i J_{f_\theta}(x_i)^\top\nabla_{z_i}\mathcal L+
\sum_i J_{g_\theta}(y_i)^\top\nabla_{u_i}\mathcal L.
\]
Representax provides rematerialized execution and a dense custom-VJP path.
The latter computes representation gradients, then replays encoder chunks
to accumulate parameter gradients. A weighted combination of Matryoshka
losses can be differentiated before replay, without a separate encoder
replay per embedding dimension. Chunk size controls memory use without
requiring a smaller scientific batch. Replay must preserve stochastic
state; finite-precision executions still require numerical checks.

Supported combinations are explicit rather than universal. Late interaction
uses rematerialized GradCache, not the dense custom-VJP path. Flattened
multimodal inputs require model-specific sample slicing. Activation
checkpointing inside an encoder chunk is a separate memory choice.
In contrast, the masked-language-modeling scaling study uses ordinary
gradient accumulation: local contributions accumulate before synchronization,
clipping and one optimizer update. It does not use contrastive GradCache.

** Data and Distributed Execution
Source mappers translate records into task examples; processors create
model-native arrays. Source-per-batch sampling draws a source according to
configured weights and consumes a complete source-local batch. This supports
a mixture of modalities over time without forcing incompatible payloads
into one batch. Example-level mixing is also available. Preprocessing and
prefetch remain outside the compiled update, and complete-interval throughput
includes any input wait visible to training.

Representax builds on Equinox, Grain, Optax and Orbax
[cite:@kidger2021equinox;@grain;@optax;@orbax]. Model transformations operate on
PyTrees, data iterators provide batches and resumable state, optimizer
transformations process gradients, and checkpoints persist training state.
JAX sharding supplies replicated and partitioned execution. DDP, FSDP and
custom parameter-sharding configurations are library capabilities; the GPU
scaling results here evaluate replicated DDP, not every sharding strategy.

** Protocol
The suite contains 13 concrete recipes, five seeds per framework, on single
RTX 4090 GPUs and a 16-chip v5e allocation: 130 runs per accelerator panel.
Five additional dense GPU runs use TorchInductor. This compiled control
does not represent a compiled baseline for every recipe. The seeds are
7, 42, 773, 1234 and 2026. They are seeded execution repetitions, not a
guarantee of independently shuffled trajectories: some historical pipelines
reuse deterministic data order.

Within a hardware/recipe pair, the intended contract matches global batch,
examples, objective settings and precision, with framework-native execution.
Historical late-interaction, reward and audio/video rows have discrepancies
described below; only complete validated replacement panels are restored as
matched-training comparisons. Encoder
chunks may differ. The other historical TPU contrastive comparisons use
per-device negatives in both frameworks; a single-GPU negative pool covers
the full batch. Cross-accelerator settings are not always identical.
Appendix [[#sec:paired-methods]] records actual models, batches, shapes,
reference integrations and known deviations.

For run \(r\), throughput is \(R_r=\sum_t B_t/\sum_t T_t\), where \(T_t\)
is the complete measured optimizer-step interval, including visible input
wait. Optimizer steps/s uses the same denominator. The tabulated framework
ratio divides median per-seed rates; the appendix shows individual paired-seed
ratios without treating consecutive updates as independent replicates.
Up to twenty warm updates per seed form a bounded timing screen, not a
demonstration of long-run stationarity. Historical native GPU late interaction
retains 15 usable intervals after first-use exclusions. Corrected GPU pairs
retain the same 19 update indices after excluding first use and the
post-checkpoint interval, whose reference timer includes save/resume overhead.
Compilation, initialization,
evaluation and checkpointing are outside this primary metric and are
reported separately where recorded.

** Results and Qualifications
Table \ref{tab:framework-throughput} shows absolute rates and relative
throughput, with substantial workload dependence. Bold values identify the
larger of the two reported medians within each workload and hardware panel,
not a statistically significant difference. GPU references in the main table
use eager execution; Appendix [[#sec:compiled-reference]] reports the compiled
dense control separately.
MPNet dense retrieval reaches 305.35 examples/s against eager Sentence
Transformers' 211.22 (1.446x), but is slightly slower than the compiled
reference. The two BERT Base sentence-pair controls are
slower on GPU, despite faster MPNet counterparts. TPU dense retrieval is
approximately tied. Historical audio/video rates remain visible, but their
ratios are withheld pending matched adapter precision and initialization.
After matching both 256-token padding and scalar-head initialization, GPU
process reward reaches 55.18 examples/s against TRL's 16.79 (3.287x).
On TPU the corrected rates are 85.26 and 9.94 examples/s (8.578x).
Both frameworks were rerun for all five seeds on each accelerator; prior
measurements remain in the evidence archive rather than being overwritten.

Several qualifications limit interpretation. Historical late interaction [L]
uses duplicated pairs with sequential native batches but shuffled reference
batches; its cached GPU reference also backpropagates summed rather than mean
gradients. On TPU, native execution ignores the configured local-negative
scope and uses 512 candidates, versus 32 for the reference. The replacement
GPU panel uses shared duplicate-free data, sequential batches, 32/256-token
limits, and corrected mean-loss cached gradients. It reaches 219.50 versus
55.18 examples/s (3.978x). Mean final NanoMSMARCO nDCG@10 is 0.7151 versus
PyLate's 0.7089 across five seeds, from initial scores 0.7123 and 0.7089.
Reference trajectories are identical across seeds with this deterministic
schedule; they are timing repetitions, not independent data draws.
The TPU replacement remains pending. The evaluation panel has only 50 queries
and scoring precision differs; this is not proof of equivalent convergence.
Outcome reward [O] uses FP32 native master parameters and optimizer moments,
but BF16 reference parameters and moments. Its rates also remain historical
execution measurements, not a matched-precision speedup.
Audio/video references [M] likewise retain BF16 trainable LoRA parameters,
where native adapters are FP32. Their default A-matrix initialization also
differs (uniform versus normal), and reference adapters were constructed
before applying the run seed. These rows require corrected controls.
Historical process-reward reference heads [I] were also constructed before
seeding. Replacement GPU and TPU panels use one shared scalar head and explicit
seeding before construction. Each TPU reference verifies identical initial and
final trainable parameters across all sixteen ranks.
Process reward selects examples fitting within 256 tokens [P], with matched
padding of 256 on GPU and 2,048 on TPU; it does not measure a representative
long-reasoning workload. TPU image-text and
V-JEPA exhibit first-seed cold-filesystem effects, and reference
pre-materialization moves some input work outside training [C]. Finally,
GPU V-JEPA uses batch one and 24 videos, whereas TPU uses batch 128 and
2,816 videos [G]. Its GPU result is a small-batch execution measurement.

Longer native-only runs complement the short reference comparisons. Dense
and CLIP adaptation each use seeds 7, 42 and 773; the multimodal study uses
those seeds for each of three strategies. We report the final scheduled
checkpoint, rather than choosing a best held-out checkpoint. These studies

state-of-the-art performance. They do not establish convergence equivalence

** Dense and Image-Text Adaptation
Dense adaptation starts from ETTIN Encoder 150M and presents 488,576
duplicate-free MS MARCO pairs once, in 3,817 updates at batch 128
[cite:@ettin;@bajaj2016msmarco]. NanoMSMARCO nDCG@10 improves from 0.0730 to
0.5794. Full-corpus TREC DL 2019 and Natural Questions retrieval scores improve
from 0.0170 to 0.5404 and from 0.0032 to 0.2922, respectively
[cite:@craswell2020trec;@kwiatkowski2019nq]. The common pretrained checkpoint is
evaluated once per dataset with the same corpora and scoring settings used for
the three trained models.

CLIP ViT-B/32 adaptation presents 588,800 COCO image-caption pairs in 1,150
updates at batch 512. Five distinct captions per image are exposed over the
run, with no repeated image within a batch. Evaluation uses a held-out
1,000-image Flickr30k panel [cite:@lin2014coco;@young2014flickr]. Both
retrieval directions improve (Table \ref{tab:learning}).
The results demonstrate useful adaptation with shared infrastructure,
rather than reproduction of CLIP's original pretraining regime.

** Text-Anchored Multimodal Adaptation
Jina v5 Omni Nano [cite:@honicke2026jina] is adapted on COCO, AudioCaps,
MSR-VTT and MS MARCO [cite:@kim2019audiocaps;@xu2016msrvtt].
All runs use batch 32, symmetric contrastive learning at temperature 0.02,
and Matryoshka dimensions 32, 64, 128, 256, 512 and 768. Three strategies
train connectors and selected delimiter embeddings, those parameters plus
rank-eight LoRA, or the full model. Each run completes 2,000 updates.
Learning rates are \(2\times10^{-4}\), \(5\times10^{-5}\), and \(10^{-5}\),
respectively.

Connector-only uniformly samples image-text, audio-text and video-text
sources; text-only examples would bypass its trainable parameters.
The other strategies uniformly sample those three sources plus text-text.
One source is chosen per update, not necessarily an equal realized number
of updates or equal compute per source. This is a comparison of complete
adaptation recipes, not a causal ablation of parameter selection at fixed
training distribution.

All three strategies improve held-out media retrieval
(Table \ref{tab:omni}; Figure [[fig:multimodal]]). Connector-plus-LoRA gives
the highest image and video scores among the tested recipes; full
fine-tuning gives the highest audio score. Connector-only preserves the
frozen text pathway's score, while the two strategies that adapt it
reduce text retrieval performance. Initial LoRA media scores differ
slightly, so changes are calculated against each strategy's own baseline.
These results expose useful adaptation and retention tradeoffs without
implying direct any-to-any supervision or validation of unseen
modality-to-modality retrieval directions.

:PROPERTIES:
:CUSTOM_ID: sec:scaling
:END:
** Fixed-Work Protocol
We use a randomly initialized 505,072,128-parameter ModernBERT masked-language
model [cite:@warner2024modernbert;@devlin2019bert], sequence length 512,
BF16 compute, FP32 parameters and AdamW state, and full activation
rematerialization. The scientific batch is fixed at 256 sequences
(131,072 input tokens) per update. Local microbatch 16 gives 16/8/4/2
accumulation rounds on 1/2/4/8 A100 SXM4 40-GB GPUs. Parameter-gradient
synchronization follows accumulation.

Seeds 7, 42 and 773 each run 21 updates, with the final 20 measured.
Token and masking hashes match across device counts within each seed.
WikiText-2 supplies repeated real text [cite:@merity2016wikitext].
This is a controlled strong-scaling workload, not complete pretraining
or a reproduction of a released ModernBERT model's training recipe.

** Throughput and Efficiency
For device count \(n\) and seed \(s\), we compute
\(S_{n,s}=R_{n,s}/R_{1,s}\) and \(E_{n,s}=S_{n,s}/n\).
Mean throughput rises from 32,015 input tokens/s on one GPU to 219,975 on
eight (Table \ref{tab:scaling}). Mean within-seed speedups are 1.968x,
3.810x and 6.871x for two, four and eight GPUs, corresponding to 98.4%,
95.2% and 85.9% efficiency. This is near-linear strong scaling through
four GPUs and high efficiency on eight for the measured workload.

* Discussion and Limitations
The evidence supports three different conclusions: the framework executes
a broad set of objectives on GPUs and multi-host TPUs; native adaptation
can improve held-out retrieval; and a fixed-work MLM workload scales
efficiently on a well-connected GPU node. None implies the others.
Table \ref{tab:capabilities} distinguishes observed execution from
unmeasured capacity or deployment claims.

The short comparison window and five repetitions do not characterize all
cache states, input stalls or long-run failures. Native streaming and
reference preprocessing sometimes place work on different sides of the
timing boundary. Consequently, the results describe the documented runnable
configurations, not intrinsic limits of JAX or PyTorch/XLA. Compilation
is visible startup cost; it is not erased by reporting amortized performance.

Learning results are also bounded. NanoMSMARCO is small, and pretrained
checkpoints may have seen related source corpora. Dataset split discipline
does not prove absence of upstream pretraining contamination. The revised
late-interaction run decreases training loss but regresses on NanoMSMARCO
from 0.7104 to 0.6925. It is retained in Appendix [[#sec:learning-details]],
rather than counted as a successful adaptation demonstration. Replacing
distillation-trained supervision with a hard-label recipe is a plausible
explanation, not an established cause.

The system's separation of objectives and execution is useful precisely
because equivalence is not automatic. Negative scope, truncation, sample
duplication and loss reduction all require explicit review. Future work
includes broader transfer evaluation, matched ablations of data and memory
strategies, resource-constrained sharding studies, and integration of
Representax tasks into other JAX training frameworks. Those integrations
remain proposed work.

* Conclusion
Representax provides a shared JAX foundation for representation-learning
research across tasks and modalities. Reference comparisons, held-out
adaptation and fixed-work scaling offer complementary evidence of its
practical utility. The framework makes established methods available as
extensible components and makes their execution choices explicit, providing
a starting point for taking new representation-learning ideas from
exploration to scale.

*Text tasks.* Dense retrieval uses the pinned Sentence Transformers MPNet
checkpoint and a 65,536-pair duplicate-free MS MARCO table, with seed-specific
permutations. Its native encoder chunks are 32; the GPU reference uses 128.
The TPU reference uses local batches of 128 and local negative pools.
Similarity uses STS Benchmark pairs and cosine regression; classification
uses a bounded duplicate-question collection and a cosine contrastive
objective with margin 0.5. Cross-encoder training uses binary labels from
3,840 pairs involving 1,920 queries. Historical late interaction uses
15,360 source-order pairs with repeated query-positive examples, temperature
0.02 and native chunk eight. It must not be conflated with the revised
hard-negative learning experiment.

*Reward tasks.* Outcome reward uses Bradley--Terry preference training on
3,840 UltraFeedback rows. Process reward uses binary process labels from
Math-Shepherd, with examples selected for four steps and mixed labels.
The latter's preparation bound is 256 tokens. Both frameworks execute padded
length 256 on GPU and 2,048 on TPU. The original GPU reference incorrectly
used 2,048 while native execution used 256; the corrected reference rerun
retains the same data, checkpoint, five seeds, optimizer and batch settings.
Its actual training tensors are checked as microbatch two by length 256.
The replacement process-reward panel also shares the initial one-row scalar
head. GPU timing uses identical update indices in both frameworks, excluding
1, 2 and the post-checkpoint update 12; TPU timing excludes 1 and 2.
Original measurements remain in the artifact correction history, not the
active throughput table.
GPU native accumulation uses microbatches four and two,
respectively, to reach the stated global batches. Both use peak learning
rate \(10^{-5}\). Outcome reward loads a BF16 base in both frameworks, but
native initialization promotes trainable leaves to FP32 before creating
optimizer state. The TRL integration retains BF16 weights and AdamW moments.
The scalar reward heads are separately initialized; equal seeds do not imply
identical JAX and PyTorch random weights. A matched numerical control must
share the starting head and align master/optimizer precision.
Historical process-reward reference construction preceded Trainer seeding and
selected one score from a newly initialized classification head without an
explicit one-label configuration. The replacement controls correct both issues.

*Multimodal tasks.* Image-text uses 3,840 COCO images with four repeated
presentations of the first caption per image in the historical timing
recipe. The longer CLIP study instead uses distinct captions. Audio-text
uses 1,920 AudioCaps clips, repeated four times; video-text uses 3,840
MSR-VTT videos. Both adapt rank-four, alpha-eight text-tower LoRA in the
3B LCO model, with the base in BF16. Native audio/video chunks are one on
GPU and two on TPU. TPU reference execution uses direct MNR at its
small local batch. These are heavier multimodal workloads than text-only
encoding, not an equal-compute comparison across modalities.
Native trainable adapters are FP32, whereas the historical Transformers
=add_adapter= path leaves them BF16. Native A matrices use a normal
distribution with standard deviation \(d_{in}^{-1/2}\); PEFT defaults to a
uniform distribution on \([-d_{in}^{-1/2},d_{in}^{-1/2}]\). Both initialize
B to zero, but this does not align subsequent optimization. The historical
reference also constructs these adapters before Trainer applies its seed.

For TPU audio specifically, batch 48 gives three examples per chip. Native
and reference runs both use device-local negative pools: each audio query
is compared against three captions, not all 48 captions in the optimizer
batch. We matched the reference runner's configured objective; its existing
PJRT integration did not connect Sentence Transformers' cross-device
embedding gather. This is a limitation of that integration, not of the
Sentence Transformers MNR objective or its GPU distributed support. Gradient
synchronization alone does not expand the contrastive candidate pool.

Native rematerialized GradCache uses chunks of two, padding each device's encoder
input to four slots and discarding the extra representation before the loss.
The reference directly encodes its three examples. Both enable layer
activation checkpointing; native execution additionally rematerializes the
encoder chunks. These are execution differences, not a change in the number
of examples or negatives contributing to the objective. All five native runs
are slower. Padding and replay are plausible contributors, but no controlled
direct-versus-cached TPU audio ablation isolates their effect on throughput.

*Predictive video.* V-JEPA uses a 12-layer, width-768 ViT-B/16 encoder,
12-layer width-384 predictor, tubelet size two and supervision at layers
2, 5, 8 and 11. The EMA coefficient is 0.99925. The initialization and
short schedule define an execution test, not a released checkpoint's quality
evaluation. GPU and TPU use 24 and 2,816 Something-Something-v2 training
videos, respectively. Per-run manifests establish this difference; a later
shared asset directory is not authoritative for an earlier run.

Except for the noted reward and predictive-video schedules, paired tasks
use AdamW with peak learning rate \(2\times10^{-5}\), zero weight decay and
gradient clipping at one; late interaction uses \(3\times10^{-6}\).
Most use one warmup update followed by cosine decay across 22 updates.
V-JEPA instead uses weight decay 0.04, no clipping, and a linear
\(10^{-4}\) to \(6\times10^{-4}\) schedule over 12,000 updates.
Native matrix computation is BF16 with FP32 accumulation in the recorded
precision policy. Frozen multimodal bases and outcome-reward loading have
the exceptions described above.

** Reference Execution and Environments
Sentence Transformers supplies dense, sentence-pair, cross-encoder and
contrastive multimodal reference paths. PyLate supplies the late-interaction
path. Reward adapters use the Torch/TRL ecosystem; predictive video uses
the official V-JEPA implementation. Launch, data and metric adapters make
these programs fit the shared measurement contract. Thus /reference/
means the documented upstream-based integration, not that every upstream
training loop was used unchanged.

GPU comparisons use PyTorch eager unless explicitly marked TorchInductor.
TPU references use PyTorch/XLA 2.9.0 and PJRT. The same program launches
on all four worker VMs, yielding sixteen ranks. Native JAX uses four
distributed processes, each controlling four local TPU devices. This is
observed multi-host execution, not multi-node GPU scaling. Sentence
Transformers' cross-device-negative helper was not connected to an initialized
Torch distributed group in this integration; the paired TPU recipes therefore
match per-device negatives rather than extending that helper. The corrected
TPU reference integration explicitly averages functional gradient outputs
before clipping and updating, checks replica identity, and requests BF16
autocast without downcasting FP32 master weights or optimizer state. Its
post-backward execution boundary is included in measured step time. These
are implementation-level comparisons, not isolated compiler benchmarks.

The native environment records JAX/jaxlib 0.11.1, Equinox 0.13.8,
Grain 0.2.18, Optax 0.2.8 and Orbax 0.12.4. GPU references record
PyTorch 2.11.0+cu128; TPU references record PyTorch 2.9.0+cpu and
Torch/XLA 2.9.0. Sentence Transformers is 5.6.1 in the principal environment;
the PyLate environment uses 5.3.0, alongside PyLate 1.6.0. Transformers
versions differ between these environments. Rather than assigning one
invented common version, the supplementary inventory preserves each
run's complete environment.

** Dense, CLIP and the Late-Interaction Regression
Dense adaptation uses ETTIN Encoder 150M (149,014,272 parameters), maximum
sequence length 128 and buckets 16/96/128. Its custom-VJP query/document
chunks are 128/64 and loss-row chunk 64. AdamW uses learning rate
\(2\times10^{-5}\), zero weight decay, clipping at one and cosine decay
with approximately 6% warmup. NanoMSMARCO has 50 queries and 5,043 documents;
TREC DL 2019 uses 43 queries over 8,841,823 passages. Natural Questions
has 3,452 queries and 2,681,468 documents and is a transfer collection,
not a training source. Evaluations
use the saved corpus/qrel manifests rather than a hand-selected candidate
set for each query.

CLIP uses images at \(224\times224\), text length 77, symmetric contrastive
loss with scale 20, GradCache chunk eight, and the same peak learning rate
and optimizer regularization as dense adaptation. Warmup is 69 of 1,150
updates. The COCO training inventory contains 117,760 images and five
captions per image. Flickr30k evaluation has 5,000 text queries and 1,000
image documents; reverse retrieval uses 1,000 image queries and 5,000
text documents. The seed-seven run resumes at update 575 and includes
export/reload checks.

The revised late-interaction recipe uses 452,096 unique query-positive
triples with one mined negative per query, global batch 512, query/document
caps 32/256, native GradCache chunk eight, temperature 0.02 and AdamW peak
learning rate \(3\times10^{-6}\). It runs 1,000 updates, with 60 warmup
updates, zero weight decay and clipping at one. It therefore cycles
through more presentations than unique triples. MaxSim evaluation scores
are accumulated in FP32. Initial nDCG@10 is 0.7104; final mean is
\(0.6925\pm0.0010\). This small-panel regression persists across three seeds.
It limits claims about this recipe, even though the system can execute
and optimize its training objective.

Source records are seed-shuffled and sampled in homogeneous batches.

* Scaling Workload Details
The controlled ModernBERT encoder uses 32 layers, width 1,280,
intermediate width 2,048, twenty attention heads and vocabulary size
32,768. Global attention occurs every third layer; local attention
uses window 128. Global/local RoPE bases are 160,000/10,000 and layer
normalization epsilon is \(10^{-5}\). The MLM head uses exact GELU.
Tokenization uses BERT Base Uncased; the larger configured output vocabulary
is part of this controlled capacity workload, not a claim of a standard
released model.

WikiText-2 supplies 23,767 nonempty rows and 2,327,462 corpus tokens.
Text is repeated as needed to supply 2,752,512 tokens for 21 updates.
The masking procedure selects 15% of eligible tokens with the standard
80/10/10 mask/random/unchanged rule. The random replacement domain is
the valid tokenizer vocabulary. This small real-text corpus is adequate
for a compute workload but not evidence of general-purpose pretraining.

AdamW uses learning rate \(10^{-4}\), weight decay 0.01 and clipping
at one. Timing includes input preparation and device placement but not
offline tokenization. The first update is excluded from warm rates.
Memory is derived from the compiled executable's arguments, outputs,
temporary buffers and aliasing, rather than equating JAX's reserved
allocator pool with live model memory.

A prior six-RTX-4090 workstation diagnostic showed substantial exposed
gradient-collective time. It motivated measurement on the A100 SXM4 node.
This is not a controlled NVLink ablation: processors, hosts and selected
microbatches also differ. The paper therefore reports the A100 strong-scaling
experiment on its own terms and does not assign all hardware differences
to one interconnect feature. FSDP capacity remains unmeasured.

* Executable Task Composition
:PROPERTIES:
:CUSTOM_ID: sec:example
:END:
The following CPU-tested example constructs a symmetric contrastive task
with Matryoshka dimensions and differentiates it using ordinary Equinox
transformations. The projection and synthetic pairs make the interface
self-contained; they are not a benchmark. New tasks can instead implement
the scalar-loss interface, and representation-aware tasks can expose the
additional boundary used by compatible modifiers and execution paths.

#+NAME: example:task-composition
#+LATEX: \begin{minipage}{\linewidth}\small
#+begin_src python
import equinox as eqx
import jax
import jax.numpy as jnp
from representax.models import DenseEncoder
from representax.tasks import build_task
from representax.tasks.modifiers import MatryoshkaModifierConfig
from representax.tasks.retrieval import (
    MNRConfig, RetrievalConfig, retrieval_batch,
)

model = DenseEncoder(8, 4, key=jax.random.key(0))
x = jnp.eye(8)
batch = retrieval_batch(
    query=x, document=x, positive_mask=jnp.eye(8, dtype=bool),
)
task = build_task(
    RetrievalConfig(), MNRConfig(symmetric=True),
    modifiers=(MatryoshkaModifierConfig(dimensions=(4, 2)),),
)
loss, gradients = eqx.filter_value_and_grad(
    lambda model: task.loss(model, batch).loss
)(model)
#+end_src
